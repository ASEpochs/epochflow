## 指标怎么算

### 意图路由链路

- `intent`：19 类细粒度主意图，取三路融合后的最终分类结果。
- `intent_group`：把细粒度意图映射到更高层的路由组，通常是通用、技术、账单这类业务域。
- `source_scores`：LLM Few-shot、Embedding 相似度、规则 Pattern 三路的原始分数或归一化分数，用来解释为什么选这个意图，不是效果指标本身。
- `4 级紧急度`：按 `LOW / MEDIUM / HIGH / CRITICAL` 做四分类，评测时可按分类 Accuracy 或 Macro-F1 统计。
- `结构化实体`：按字段做 exact match，或在多字段场景下计算 field-level precision / recall / F1。

### 常用公式

- `Accuracy = 正确预测数 / 总样本数`
- `Precision = TP / (TP + FP)`
- `Recall = TP / (TP + FN)`
- `F1 = 2PR / (P + R)`
- `Macro-F1 = 各类别 F1 的平均值`

### LLM-as-Judge 能做什么

- 可以：辅助标注模糊样本、判断回复质量、校验实体归一化、给路由解释打分、生成回归分析建议。
- 不适合单独承担：最终的 Accuracy、Precision、Recall、F1 统计。
- 原因：这些分类指标需要稳定的 gold label 和可复现的预测输出，最终应由评测脚本基于标注集计算；LLM-as-Judge 更适合做标注辅助和主观质量评分。



## 逐条说明


1. `19 类细粒度意图 + 4 级紧急度 + 3 路融合`：意思是系统不是只分“技术/账单/咨询”这种大类，而是能识别更细的业务问题，并把紧急程度单独标出来。
2. `约 500 条自建意图评测用例`：意思是项目有一批自己的评测样本，可以直接验证意图识别效果，不是只能靠人工感觉。
3. `准确率 / 宏平均 F1 / 单类精确率 / 单类召回率 / 单类 F1`：意思是把分类任务常见的指标都写全，方便面试官判断模型到底是整体准，还是某些类别特别弱。
4. `3 类 Agent 路由`：意思是系统不是一个通用 Bot，而是能把问题分给通用、技术、账单三个不同处理角色。
5. `6 篇默认知识库文档`：意思是项目开箱就有基础知识库，不是空仓库，能覆盖退款、订单、账户、技术、会员和配送等常见场景。
6. `500 字切片 + 3 路查询改写 + 并行召回`：意思是长文档先拆块，再从多个角度改写问题去检索，避免只搜一个关键词漏掉相关内容。
7. `RAG 回答准确率 65% → 83%`：意思是接入检索增强后，答案更贴近知识库事实，不再主要靠模型“凭感觉回答”。
8. `RAG 召回率提升约 5 个百分点`：意思是改写、并行召回和重排后，能找到更多相关文档片段，漏检更少。
9. `Redis 24h TTL + 15 条压缩阈值 + 最近 5 条保留`：意思是短期会话记忆只保留当天有效内容，超过阈值会压缩成长摘要，避免上下文无限变长。
10. `3 类 Skills 热加载`：意思是客服规则不是写死在 prompt 里，而是按业务场景拆成可替换的规范文件，运行时也能更新。
11. `5000 字 prompt 注入上限`：意思是 Skills 不会无限膨胀，系统会控制注入长度，避免 prompt 太长拖慢或带偏模型。
12. `5 组端到端对话评测`：意思是项目不仅测单条意图，还会跑真实对话流程，看完整链路会不会出问题。
13. `4 维 Judge 评分`：意思是回复质量不是只看“像不像人话”，而是分别看相关性、准确性、完整性和帮助性。
14. `0.75 通过阈值`：意思是评测有明确及格线，不是跑完就算过。
15. `5% 回归检测`：意思是如果新版本比旧版本退化超过 5%，系统会把它标成 regression，方便你发现改坏了哪里。
16. `300s 工具缓存 + 30s 超时 + 熔断 + fallback`：意思是知识库检索也做了稳定性保护，慢了会超时，连续失败会熔断，出问题时会返回降级结果。
17. `/monitor` 和 `/metrics`：意思是项目有运行观测入口，能看 Agent 和工具的健康状态，不是黑盒。
18. `精简投递版`：意思是把上面的能力浓缩成 3 条，适合简历页数紧张时直接用。 
19. HR 开场白：意思是把项目经历浓缩成一段能直接发给 HR 的自我介绍，强调你做的是完整 Agent 工程，而不是普通聊天 Demo。

## 指标口径补充

如果面试官追问第一条的数据来源，可以直接按这个口径讲：

- `source_scores` 不是结果指标，而是三路输入证据分数，分别来自 LLM Few-shot、Embedding 相似度和规则 Pattern。
- `intent` / `intent_group` / `4 级紧急度` / `结构化实体` 是路由链路的输出，用来决定该走哪个 Agent、是否要澄清、是否要升级。
- `91.3%`、`0.89`、`0.88-0.94` 这类数字来自约 500 条人工标注样本，按预测结果和标准答案逐条对比后，用普通分类指标计算出来。
- `Accuracy = 预测正确的样本数 / 总样本数`。
- `Macro-F1 = 19 个意图各自算 F1，再求平均`。
- `单类 precision / recall / F1` = 每个意图单独统计，再看哪些类弱、哪些类强。
- `LLM-as-Judge` 主要用于回复质量评分，不负责这组分类指标的主计算。

## 面试追问版

1. 细粒度意图识别与路由链路：我不是只做一个单模型分类器，而是把 LLM Few-shot、Embedding 相似度和规则 Pattern 做三路融合。线上先做统一预处理，再让三路分别给出候选意图和分数，最后按权重和规则做最终决策；`intent_group` 用来做粗路由，`source_scores` 用来解释为什么判成这个意图，`4 级紧急度` 用来决定是否澄清、升级或直接处理。
2. 意图评测数据：我单独整理了约 500 条自建评测样本，每条都有人为 gold label。评测时跑完整识别流程，再用脚本把预测结果和 gold label 做逐条对比，算出 Accuracy、Macro-F1 和各类的 Precision / Recall / F1；所以简历上的 91.3% 不是拍脑袋，是离线评测集算出来的。
3. 意图门控 RAG：我先用意图判断决定要不要检索，只有业务类问题才进知识库，问候、转人工、无意图问题直接跳过。真正检索时会做查询改写、并行召回、去重、重排，再把 Top-K 片段拼回上下文，避免模型在不该查的时候查，也避免只靠一个关键词漏召回。
4. Redis + ChromaDB 分层记忆：短期会话信息放 Redis，控制 TTL 和消息条数；长程记忆和用户画像放 ChromaDB，超过阈值后先压缩再写回。这样既能保留当前轮上下文，又不会让 prompt 无限膨胀，线程池是为了避免同步向量库访问卡住主链路。
5. 动态 Skills：我把通用客服、技术排障、账单退款这些业务规范拆成独立 Skills 文件，不直接写死在代码里。路由到不同 Agent 时再按场景注入对应 Skills，并提供热更新接口，这样规则改动不用重新发版，Agent 之间的职责也更清晰。
6. Monitor + LLM-as-Judge：运行时我会记录 Agent 成功率、工具耗时、连续失败次数这些观测数据，再把它们汇总成路由惩罚项，影响后续 Agent 选择；评测侧则真实调用 Orchestrator 生成回复，再用 LLM-as-Judge 从相关性、准确性、完整性和帮助性四个维度打分。前者解决线上稳定性，后者解决回答质量和回归检测。
7. 说明gold label 就是“标准答案 / 真实标签”。 在你的评测里，就是人工标注好的正确意图。 比如用户说“为什么扣了两次款？”，模型预测成 payment_issue，而标注表里这条的 gold label 也是 payment_issue，那就是预测正
