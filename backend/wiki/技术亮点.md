# EchoMind 技术亮点

本文档按“当前代码真实实现”重写，重点说明 EchoMind 为什么不再是“单 Agent + prompt 变体”，而是一个**路由驱动的多 Agent 客服运行时**。

当前链路不是先写答案再补能力，而是先做结构化判断，再决定谁来处理、能用哪些工具、要不要并行、是否升级、最后如何回写记忆和监控。

## 先看结论

| 能力 | 关键模块 | 价值 |
|---|---|---|
| 三路融合意图识别 | `core/intent_recognizer.py` | 让路由建立在结构化判定上，而不是关键词猜测 |
| 路由驱动的多 Agent 编排 | `agents/agent_orchestrator.py` | 支持主 Agent、辅助 Agent、升级 Agent 协作 |
| 共享工具 + 角色白名单 | `agents/agent_orchestrator.py`、`agents/tools.py` | 工具可复用，但调用边界可控 |
| 意图驱动 RAG | `api/main.py`、`mcp/tool_manager.py`、`mcp/knowledge_base.py` | 只在该搜的时候搜，减少噪声 |
| 三层记忆 | `memory/conversation_memory.py` | 兼顾短期上下文、跨轮线索和长期偏好 |
| 动态 Skills 注入 | `core/skill_loader.py` | 业务规则可热更新，不用每次改代码 |
| 在线监控与路由降权 | `monitor/performance_monitor.py` | 把运行时质量反馈回路由层 |
| 端到端评测 | `evaluation/evaluator.py` | 支持意图识别和回复质量的持续回归 |

## 总体架构

```text
用户请求
  -> api/main.py
  -> MemoryManager.get_context()
      - Redis 工作记忆
      - ChromaDB 情景记忆 episodic
      - ChromaDB 用户画像 user_profile
  -> IntentRecognizer.recognize()
      - LLM Few-shot
      - Embedding 相似度
      - Pattern 规则
      - 输出 intent / intent_group / source_scores / urgency / entities
  -> _build_knowledge_context()
      - 仅对业务类问题触发知识检索
  -> AgentOrchestrator.run()
      - 路由到主 Agent
      - 必要时并行调用辅助 Agent
      - 升级场景交给 EscalationAgent
  -> ResponseComposer
      - 合并多 Agent 输出
  -> MemoryManager.add_message()
  -> MemoryManager.update_profile()
  -> PerformanceMonitor / EndToEndEvaluator
```

## 亮点一：三路融合意图识别

**文件**：`core/intent_recognizer.py`

### 解决的问题

客服路由最怕两件事：

1. 把“退款”误判成“账单查询”
2. 把“登录报错 + 重复扣款”这种复合问题拆错

如果只靠关键词，鲁棒性差。只靠 LLM，成本高、延迟高、行为不稳定。EchoMind 的做法是把三种方法一起用：

- `LLM` 负责语义理解和上下文判断
- `Embedding` 负责和模板样本做相似度匹配
- `Pattern` 负责零延迟兜底和高精度规则命中

### 具体怎么做

`recognize()` 会并行启动 LLM 和 Embedding 识别，Pattern 同步执行，最后通过加权投票合并：

- LLM 权重最高
- Embedding 负责补足常见表达
- Pattern 负责兜底和细粒度意图纠偏
- 低于阈值时回退到 `OTHER`

### 输出不只是 intent

最终输出的是结构化结果，不是一个分类标签：

- `intent`
- `intent_group`
- `confidence`
- `source_scores`
- `urgency`
- `entities`

其中 `entities` 会规则抽取：

- `order_id`
- `date`
- `amount`
- `error_code`

这让后面的路由、升级、知识检索都可以直接消费结构化信息。

### 紧急度怎么来的

紧急度是 4 级：

- `LOW`
- `MEDIUM`
- `HIGH`
- `CRITICAL`

规则来源有两层：

- 命中“紧急 / asap / 立刻”等关键词时直接抬升
- 若意图是转人工或投诉，也会提升到更高紧急度

### 面试时怎么讲

> 我没有把意图识别做成单一分类器，而是做成了三路融合。LLM 负责语义，Embedding 负责相似度，Pattern 负责高精度规则兜底。最后输出的不只是 intent，还包括 intent_group、source_scores、urgency 和 entities，直接给后续路由和升级使用。

## 亮点二：路由驱动的多 Agent 编排

**文件**：`agents/agent_orchestrator.py`

### 和早期版本的区别

早期版本更像：

```text
用户消息 -> 一个编排器 -> 几个只改 prompt 的 Agent
```

现在不是。当前版本是：

```text
意图识别 -> 路由决策 -> 主 Agent / 辅助 Agent / 升级 Agent
           -> 可能并行执行 -> ResponseComposer 合并
           -> 结果写回记忆 -> Monitor 反馈路由
```

这意味着多 Agent 的差异不只在 prompt，而是体现在：

- `AgentProfile`
- 工具白名单
- 输入/输出契约
- 路由逻辑
- 运行时统计
- 监控反馈

### 当前有哪些角色

默认有 4 类角色：

- `GeneralAgent`
- `TechnicalAgent`
- `BillingAgent`
- `EscalationAgent`

其中 `EscalationAgent` 不再假装“继续回答”，而是负责标准化交接。

### 为什么 `pool` 是 list

`_pool: Dict[AgentType, List[BaseAgent]]` 这里用 `list`，不是因为现在就有很多实例，而是为了支持：

- 同角色多实例扩展
- 同类型不同模型配置
- 在线表现差异化路由
- 后续压测、灰度和降级

当前默认每类只有 1 个实例，但结构已经预留了横向扩展能力。

### 路由怎么做

路由不是纯关键词，主要看这些信号：

- 意图类别
- 紧急度
- 结构化实体
- 领域关键词
- Agent 在线表现

对于复合问题，系统会给出 `primary_agent` 和 `supporting_agents`，然后并行执行。

### 面试时怎么讲

> EchoMind 的多 Agent 不是 prompt-only。现在每个角色都有自己的契约、工具边界和路由位置，复杂问题还能主辅协作并行处理，运行表现还会反馈到下一轮路由里。

## 亮点三：共享工具体系 + 角色白名单

**文件**：`agents/agent_orchestrator.py`、`agents/tools.py`

### 解决的问题

客服 Agent 不能“什么都能调”，否则会出现两个问题：

- 能力边界失控
- 工具重复定义，维护成本高

### 当前实现

工具被统一抽象成 `AgentToolSpec`，再按角色注入。Agent 调用工具时会做：

- 白名单检查
- JSON Schema 参数校验
- 异步执行支持
- 调用结果回填给模型

### 当前分层

- 通用工具
- 技术工具
- 账单工具
- 升级工具
- 共享 RAG 工具

### 设计意义

- RAG 可以所有 Agent 共用
- 但每个 Agent 仍然只能调用自己的能力范围
- 避免“一个 prompt 换个身份就能乱调工具”

### 面试时怎么讲

> 我把工具做成统一的工具层，再按角色做白名单控制。这样能力可以共享，边界又不会失控，工程上比把工具写进各自 prompt 里更稳。

## 亮点四：意图驱动的 RAG

**文件**：`api/main.py`、`mcp/tool_manager.py`、`mcp/knowledge_base.py`

### 解决的问题

不是所有问题都适合检索。

- 问候、闲聊、转人工，不需要查知识库
- 订单状态、退款规则、发票政策，这类业务问题才适合检索

### 当前链路

```text
用户消息
  -> 先做意图判断
  -> 再决定是否检索知识库
  -> 仅在业务类请求中构建知识上下文
```

### 为什么这样做

- 减少无效检索
- 避免把无关文档塞进上下文
- 降低回答被知识噪声干扰的概率

### 工程特征

检索层不是简单向量搜索，而是围绕真实客服链路做的工具化设计：

- 查询改写
- 并行召回
- 合并去重
- fallback
- 缓存
- 熔断

### 面试时怎么讲

> 我把 RAG 放进了主链路，但不是见词就搜，而是先由意图判断决定是否检索。这样既提升业务问题的召回，也避免闲聊类请求被知识库噪声污染。

## 亮点五：三层记忆管理

**文件**：`memory/conversation_memory.py`

### 解决的问题

客服对话既要记住当前轮，又不能把所有历史都塞进 prompt，还要保留跨会话偏好。

### 三层记忆

- **工作记忆**：Redis，保存当前会话最近消息
- **情景记忆**：ChromaDB `episodic`，保存压缩摘要
- **用户画像**：ChromaDB `user_profile`，保存长期偏好和稳定实体

### 当前实现特点

- 工作记忆超过阈值会自动压缩
- 摘要不是简单拼接，而是合并更新
- `to_prompt_text()` 只拼最近少量消息
- 用户画像按 `user_id` 稳定存储

### 为什么要分层

因为三种信息的时间尺度不同：

- 当前轮是短期上下文
- 历史摘要是跨轮线索
- 用户画像是长期偏好

放在一个窗口里，效果通常会互相干扰。

### 面试时怎么讲

> 我把记忆拆成工作记忆、情景记忆和用户画像三层，分别对应当前轮、跨轮线索和长期偏好。这样既控制上下文长度，也保留了跨会话连续性。

## 亮点六：动态 Skills 注入

**文件**：`core/skill_loader.py`

### 解决的问题

知识库回答的是“事实是什么”，Skills 约束的是“应该怎么处理”。

比如：

- 技术故障要先收集错误码和环境
- 账单问题不能随便承诺到账时间
- 涉及隐私和安全时要避免让用户暴露敏感信息

### 当前实现

Skills 支持热加载，常见格式包括 Markdown、JSON、TXT。系统会按以下条件决定是否注入：

- Agent 类型
- 用户消息关键词
- `enabled` 开关

### 为什么重要

业务规范可以独立更新，不需要每次都改主代码。

### 面试时怎么讲

> Skills 解决的是行为边界和处理规范，不是事实问答。它和知识库分工不同，而且可以热更新，业务规则调整时不需要改代码主链路。

## 亮点七：Monitor 在线观测与路由降权

**文件**：`monitor/performance_monitor.py`

### 解决的问题

多 Agent 系统不能只在设计时看起来合理，还要在运行时保持健康。

某个 Agent 即使语义上最合适，也可能因为延迟升高、成功率下降、工具异常而不再适合继续接单。

### Monitor 做了什么

- 定时采集 Agent 成功率和平均延迟
- 定时采集工具成功率和延迟
- 做异常检测
- 生成告警和建议
- 把结果写回 `monitor_penalty`

### 这意味着什么

路由不是静态的。  
在线表现差的 Agent，后续会被自动降低选中概率。

### 面试时怎么讲

> 我把监控结果接回了路由层，而不是只做展示。Agent 的成功率、延迟和异常情况会影响 routing_score，这样系统能根据在线表现自动避开状态变差的节点。

## 亮点八：端到端评测闭环

**文件**：`evaluation/evaluator.py`

### 解决的问题

如果没有评测，优化只能靠感觉。

### 当前评测内容

- 意图识别 Accuracy
- Macro-F1
- 单类 Precision / Recall / F1
- 对话回复质量
- 回归检测
- 优化建议

### LLM-as-Judge

回复质量由 LLM 从四个维度打分：

- relevance
- accuracy
- completeness
- helpfulness

### 为什么这重要

它让项目从“能跑”变成“能量化迭代”。

### 面试时怎么讲

> 我不只做了多 Agent 编排，还把意图识别和回复质量都接进了评测闭环。这样系统不是靠感觉调，而是能用 Accuracy、Macro-F1 和 LLM-as-Judge 做持续回归。

## 数据存储设计

EchoMind 里 ChromaDB 同时承担知识库和长期记忆。

| Collection | 写入来源 | 查询用途 |
|---|---|---|
| `knowledge_base` | 默认文档、`/knowledge/add`、`/knowledge/upload` | `/search` 和 `/chat` 的知识检索 |
| `episodic` | 工作记忆压缩后的摘要 | 下一轮对话的历史线索 |
| `user_profile` | 每次 `/chat` 后异步更新 | 个性化和长期偏好 |

## 一句话总结

EchoMind 的技术亮点不在单点模块，而在于它把以下能力串成了闭环：

- 识别问题
- 路由角色
- 协作执行
- 检索知识
- 管理记忆
- 注入规则
- 监控质量
- 量化评测

一句话概括：

> EchoMind 是一个可观测、可评测、可降级的多 Agent 客服运行时，而不是单纯的聊天机器人。
